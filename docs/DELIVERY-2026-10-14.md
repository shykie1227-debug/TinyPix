两个形态内容等价（同一份 publish 输出 + 同一份 FFmpeg 引擎），区别只在分发方式：

- **单文件 `TinyPix.exe`**：双击即用。首次启动时把自包含的运行时与 `Engines/` 释放到临时目录，
  因此**首次启动比后续慢**（160 MB 解压量），之后走缓存。适合"拷一个文件就能跑"。
- **便携 ZIP**：解压到任意目录（U 盘也行），双击目录里的 `TinyPix.exe`。**启动更快**，
  且 `Engines/`、`Logs/`、`Settings/` 都在解压目录里，便于排查和迁移。这是 `LOCAL_RULES.md` §2 的正式形态。

两者均：无需安装、无需管理员权限、无 MSIX/MSI/安装器、不写注册表业务键、可离线运行。

## 3. 打包命令（在 Windows 上，需 .NET SDK 10.0.302）

```powershell
# 便携 ZIP（正式形态）→ artifacts/TinyPix-4.0-Windows-x64-Portable.zip
pwsh ./build/publish-portable.ps1

# 单文件 exe（可选形态）→ 输出目录里单个 TinyPix.exe
pwsh ./build/Publish-SingleFile.ps1
```

`publish-portable.ps1` 会自动调用 `build/Get-FfmpegEngine.ps1` 拉取并校验引擎；
离线环境可用 `-CacheDir <路径>` 指向已下载的 zip 复用。

GitHub Actions 走 `.github/workflows/build-exe.yml`（`windows-latest`），
同时产出两个产物并上传 artifact，另含三个库的单测与 LGPL 编码器门禁。

## 4. 干净机器验证步骤

前提：一台没装过 .NET、没有本仓库的 Windows 10/11 x64 机器（19041 及以上）。

1. **取包**：把 `TinyPix.exe`（或便携 ZIP 解压后的整个目录）拷到目标机，例如 `D:\TinyPix\`。
2. **断网**（可选但推荐）：拔网线或关 Wi-Fi，用于验证离线能力。
3. **双击启动**：直接双击 `TinyPix.exe`。
   - 期望：主窗口出现，左侧文件区、中间工作区、右侧参数区、任务队列四分区齐全。
   - 首次启动（单文件形态）会有 10–60 秒自解压，属正常。
4. **引擎自检**：设置里看输出目录，或打开便携目录确认 `Engines/ffmpeg.exe` 存在。
   命令行可验：`Engines\ffmpeg.exe -hide_banner -encoders | findstr openh264` 应能看到 `libopenh264`。
5. **功能冒烟**：
   - 拖入一个 mp4 → 选"视频输出" → 格式 mp4 → 开始 → 输出目录应生成 `xxx_转换.mp4`。
   - 同一个文件 → 选"GIF 制作" → 开始 → 生成 `xxx_GIF.gif`。
   - 确认**源文件哈希未变**（这是 `LOCAL_RULES.md` 的验收门槛）：
     `certutil -hashfile 输入.mp4 SHA256` 前后两次应完全一致。
6. **便携性**：把整个目录复制到另一台机器或 U 盘再跑一遍，应同样可用；不写 `Program Files`、不写注册表业务键。

## 5. 为什么"窗口启动"这一项要你手动确认

自动化链路（Parallels 的 `prlctl exec`）是以 **SYSTEM、非交互会话**执行进程的
（`UserInteractive=False`，没有桌面站）。WinUI 的 `Microsoft.UI.Input.dll` 在无桌面会话下
必然 fail-fast，退出码 0xC000027B / 0xC0000602。

为排除"是我们代码的问题"，我另外建了一个**不含任何本项目 XAML 的最小 WinUI 应用**
（只有一个 `TextBlock`）在同一台 VM、同样的 publish 参数下跑——**同样崩溃**。
所以这是执行环境限制，不是 TinyPix 的缺陷；真实双击启动不受影响。

**需要你做的一步**：在虚拟机（或任何 Windows 机器）里用资源管理器打开目录，
双击 `TinyPix.exe`，确认主窗口出现。这一步无法用当前自动化手段替代。
